## BLOCKCHAIN FUNDAMENTALS

**Q1. What is a blockchain?**
A blockchain is a distributed, append-only ledger of records (blocks) linked together using cryptographic hashes. Once data is recorded in a block and confirmed by the network, it is extremely difficult to alter without changing all subsequent blocks. This makes it tamper-resistant and publicly auditable.

**Q2. What is Ethereum?**
Ethereum is an open-source, programmable blockchain platform. Unlike Bitcoin which is mainly a currency, Ethereum allows developers to deploy smart contracts — self-executing code stored on the blockchain. Ethereum uses Ether (ETH) as its native currency.

**Q3. What is a smart contract?**
A smart contract is a program written in Solidity that runs on the Ethereum blockchain. It executes automatically when predefined conditions are met. In CharityChain, the smart contract handles: charity registration, verification status, and processing donations.

**Q4. What is a transaction hash?**
A transaction hash (txHash) is a unique 64-character hexadecimal string that identifies a specific transaction on the blockchain. Example: `0x82A3...91F2`. It is generated by hashing the transaction data and serves as proof that the transaction occurred.

**Q5. What is a block?**
A block is a container that holds a set of transactions. Each block contains: block number, timestamp, list of transactions, previous block's hash, and its own hash. Blocks are chained together — changing one block would invalidate all following blocks.

**Q6. What is gas in Ethereum?**
Gas is the unit that measures the computational effort required to execute a specific operation on Ethereum. Every transaction requires gas to compensate miners/validators. In CharityChain, donors pay gas fees (in test ETH) when sending donations through the smart contract.

**Q7. What is a testnet?**
A testnet is a test version of a blockchain network. It uses fake tokens with no real-world value. CharityChain uses Hardhat's local testnet (chainId: 31337). For external testing, Sepolia testnet can be used. Testnets allow developers to test without risking real funds.

**Q8. What is a wallet address?**
A wallet address is a 42-character hexadecimal identifier (example: 0x1234...ABCD) derived from a user's public key. It is the Ethereum equivalent of a bank account number. In CharityChain, charity wallet addresses are registered in the smart contract to receive donations.

## SMART CONTRACTS & SOLIDITY

**Q9. What language is used to write smart contracts?**
Solidity — a statically typed, contract-oriented programming language specifically designed for writing smart contracts on Ethereum. Example from our project: `pragma solidity ^0.8.20;`

**Q10. What is OpenZeppelin?**
OpenZeppelin is a library of secure, audited, reusable smart contract components. CharityChain uses:
- `ReentrancyGuard` — prevents reentrancy attacks on the `donate()` function
- `Ownable` — restricts admin-only functions like `verifyCharity()` to the contract owner

**Q11. What is reentrancy and how do you prevent it?**
Reentrancy is an attack where a malicious contract calls back into the original contract before the first execution finishes — potentially draining funds. We prevent it using `ReentrancyGuard` from OpenZeppelin, which adds a `nonReentrant` modifier to the `donate()` function.

**Q12. What events does your smart contract emit?**
- `CharityRegistered` — when a charity is registered on-chain
- `CharityVerified` — when admin approves a charity
- `CharityRejected` — when admin rejects a charity
- `DonationReceived` — when a successful donation is made (includes donor, charity, amount, donationId, timestamp)

Events are stored in transaction logs and provide a permanent, queryable audit trail.

**Q13. What security checks does your smart contract perform?**
1. Only the owner (admin) can register, verify, or reject charities
2. Only verified charities can receive donations
3. Zero-value donations are rejected: `require(msg.value > 0)`
4. Zero-address charity is rejected: `require(_charityWallet != address(0))`
5. Duplicate charity registration is rejected
6. Self-donation is rejected: `require(msg.sender != _charityWallet)`
7. ReentrancyGuard on the donate function

**Q14. Why do you use `call()` instead of `transfer()` for sending ETH?**
`transfer()` has a fixed 2300 gas limit which can fail if the recipient is a smart contract. `call()` forwards all available gas and is the recommended pattern since EIP-1884. We use: `(bool success, ) = _charityWallet.call{value: msg.value}("");`

## METAMASK & ETHERS.JS

**Q15. What is MetaMask?**
MetaMask is a browser extension that acts as an Ethereum wallet. It allows users to manage their private keys securely, sign transactions, and interact with DApps (decentralized applications). In CharityChain, MetaMask is used to connect donor wallets and confirm donation transactions. The private key never leaves MetaMask.

**Q16. What is Ethers.js?**
Ethers.js is a JavaScript library for interacting with the Ethereum blockchain. CharityChain uses it to: connect to the network, create contract instances, call contract functions, send transactions, and parse transaction receipts.

**Q17. How does a donor send a donation in your system?**
1. Frontend calls `donateToCharity(signer, charityWallet, amount)` from `blockchain.js`
2. Ethers.js creates a contract instance with the signer
3. It calls `contract.donate(charityWallet, { value: parseEther(amount) })`
4. MetaMask opens showing transaction details
5. User confirms → transaction is sent to Hardhat node
6. Smart contract validates → transfers ETH → emits `DonationReceived`
7. `tx.wait(1)` waits for 1 block confirmation
8. Transaction hash is returned and displayed

## MONGODB & BACKEND

**Q18. Why do you use MongoDB alongside blockchain?**
Blockchain is expensive for storage (gas costs) and not suitable for storing large text, images, or personal data. MongoDB stores: user profiles, charity descriptions, contact info, admin notes, and application metadata. It enables fast search/filter without reading the blockchain every time.

**Q19. What is JWT and how do you use it?**
JWT (JSON Web Token) is a compact, self-contained token used for authentication. When a user logs in, the server signs a JWT with a secret key and sends it back. The client includes this token in every API request as `Authorization: Bearer <token>`. The server verifies it on each request without querying the database.

**Q20. How do you hash passwords?**
Using `bcryptjs` with 12 salt rounds. The `passwordHash` field is never returned in API responses (using `select: false`). Comparison uses `bcrypt.compare()`. Passwords are never stored in plain text.

**Q21. What is the difference between on-chain and off-chain data in your system?**
- **On-chain**: Donor wallet, charity wallet, donation amount, timestamp, tx hash, smart contract events. This data is publicly verifiable and tamper-resistant.
- **Off-chain (MongoDB)**: Charity name/description, user emails, passwords (hashed), verification documents metadata, admin notes. This data is private, searchable, and cheaper to store.

## PROJECT-SPECIFIC

**Q22. Does blockchain prove that a charity is genuine?**
No. Blockchain records are tamper-resistant, but they don't verify the real-world legitimacy of a charity. CharityChain uses **administrator verification** — an admin reviews each charity's application and approves it. The "Verified" badge means the admin has reviewed the application, not that blockchain automatically certified it.

**Q23. Why can't unverified charities receive donations?**
The smart contract checks: `require(charities[_charityWallet].status == CharityStatus.Verified, "Charity not verified")`. This ensures that even if someone tries to send ETH directly to the contract for an unverified charity, the transaction will revert. The check is enforced at the contract level, not just the UI.

**Q24. What happens if a donor rejects the MetaMask transaction?**
MetaMask throws an error with code `4001` (user rejected). The `DonationModal` catches this and shows an error message. The smart contract is never called, no ETH is spent, and no blockchain record is created.

**Q25. How does the donation reach the charity?**
The smart contract's `donate()` function directly transfers ETH to the charity wallet using `_charityWallet.call{value: msg.value}("")`. The contract does not hold funds — ETH passes through it in the same transaction.

**Q26. What is the role of the transaction hash in your system?**
The transaction hash is the unique identifier of the blockchain transaction. It serves as:
- Proof that the donation occurred
- A reference stored in MongoDB for linking off-chain records to on-chain data
- A link for the blockchain explorer (on Sepolia testnet)
- The display ID in the donation receipt shown to users

**Q27. What are the three user roles and how are they protected?**
1. **Donor** — authenticated via JWT, can browse charities and donate
2. **Charity** — authenticated via JWT, can only see their own dashboard
3. **Admin** — authenticated via JWT + `authorizeRoles("admin")` middleware
Each role has separate route protection. A donor cannot access admin routes — they get a 403 Forbidden response.

**Q28. What would happen if you stored all data on the blockchain?**
- Personal data (emails, names) would be publicly visible — privacy violation (GDPR issues)
- Large text (descriptions) would cost enormous gas fees
- Passwords should NEVER be on blockchain — anyone could read them
- Performance would be very poor for searching/filtering
- So we use a hybrid: sensitive/large data in MongoDB, transaction proofs on blockchain

**Q29. What is Hardhat?**
Hardhat is an Ethereum development environment. It provides: a local blockchain node for testing, a Solidity compiler, test runner with Chai/Mocha, deployment scripts, and debugging tools. CharityChain uses Hardhat as the local blockchain network during development.

**Q30. What are the limitations of your system?**
1. Uses testnet only — not production-ready
2. Admin verification is centralized — a single point of trust
3. No IPFS for document storage — only metadata
4. No real blockchain explorer for local Hardhat network
5. Charity wallet verification is not cryptographic — admin manually checks
6. Smart contract owner is a single address — no multi-sig governance
7. No email notifications for charity status updates
